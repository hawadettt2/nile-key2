4. مبادئ التنفيذ الملزمة
1. الدليل قبل القرار: لا تُغيّر صلاحية أو Prompt قبل توثيق المشكلة بمخرج CLI أو نص ملف أو سجل تشغيل.

3. أقل صلاحية لازمة: لا تمنح أداة لمجرد أن وكيلًا طلبها في Prompt؛ يجب أن تكون ضرورية لدوره.
4. Bash مسار تنفيذ وكتابة محتمل: لا تعتبر edit: deny أو قيد أنماط Edit حاجزًا كافيًا إذا كان bash مسموحًا على نحو واسع.
5. الموافقة النصية ليست قيدًا تقنيًا: عبارة «اطلب موافقة المالك» لا تكفي إذا كانت الأداة ذات الصلة allow ولا تفرض موافقة فعلية.
6. لا افتراض للوراثة: يجب وضع قواعد اللغة والسلوك الجوهرية في Prompt الفعّال للوكيل نفسه، أو إثبات آلية الوراثة باختبار موثق.
7. مصدر حقيقة واحد: يجب أن يكون لكل قيمة فعالة مصدر معتمد واضح. لا تُترك التعريفات المتكررة أو المتعارضة دون تفسير.
8. لا تعديل عام ضمنيًا: إعدادات ~/.config/kilo/ عامة للمستخدم؛ لا تُعدّل ضمن هذه الخطة إلا بقرار مستقل وصريح.
9. لا مساس بالأعمال السابقة: لا تعديل على Suppliers أو Backend أو Frontend أو قاعدة البيانات أو Docker أو أي مهمة مكتملة خارج نطاق الوكلاء.
10. لا Commit ولا Push تلقائيًا: تُعرض الفروقات أولًا، ولا يُنفّذ الحفظ في Git إلا بإذن صريح.
11. مرحلة واحدة في كل مرة: لا ينتقل Kilo إلى المرحلة التالية بعد إنهاء مرحلة دون موافقة المالك.
12. مهمة واحدة لكل برومبت: تُجزأ الأعمال الكبيرة إلى طلبات قصيرة محددة؛ لا يُطلب من Kilo تنفيذ الخطة كلها في تشغيل واحد.
13. العربية إلزامية في مخرجات العمل: يكتب الوكيل تقاريره وشرح قراراته بالعربية، مع إبقاء أسماء الأدوات والملفات والمعرّفات التقنية كما هي.
14. لا نجاح بالتصريح: عبارة «سأفحص» أو STANDALONE_OK ليست نتيجة قبول. يجب إظهار المخرجات والأدلة.
15. عند التعثر: يذكر Kilo الأمر الذي تعذر، ورسالة الخطأ، والجزء الذي اكتمل، ولا ينتقل إلى حل بديل أو تعديل غير معتمد.
16. سلامة المصدر: لا يُنسخ أي ملف إلى مجلد الخطة قبل التأكد من أنه يحتوي مادة الخطة فقط، وأنه خالٍ من النصوص الملصقة أو الأسرار.
17. تقليل المخرجات: لا تُطبع ملفات إعداد كاملة أو مخرجات ضخمة إذا كانت قد تحتوي قيمًا شخصية أو سرية؛ يُعرض الجزء اللازم بعد التنقيح.
18. حالة Git المحلية ليست بالضرورة حالة الخادم: عند منع `fetch`، تُوصف `origin/main` بأنها مرجع محلي مخزن قد يكون قديمًا، ولا يُدّعى التحقق من آخر حالة بعيدة.
19. إثبات عدم التغيير: لا يكفي قول «لم أعدّل شيئًا»؛ يجب مقارنة حالة الملفات قبل المهمة وبعدها، وتحديد أي ملفات أُنشئت أو تغيرت.
20. لا تُصلح أثناء التدقيق: اكتشاف خطأ أو سر أو تعارض لا يمنح إذنًا بإصلاحه. يوثق العائق ويطلب قرار المالك.
21. لا تُعدّل الملفات المتداخلة مع تغييرات سابقة غير محسومة. عند وجود تداخل، يتوقف Kilo ويطلب مقارنة مستقلة قبل التحرير.
22. لا تفترض أن إصدار إضافة VS Code يساوي إصدار CLI؛ سجّل كل إصدار من مصدره إن كان كلاهما مستخدمًا.

لكل وكيل، سجّل بشكل منفصل:
- التعريف الأساسي: مدمج، ملف عام، ملف مشروع، أو Inline.

- المسار الدقيق لكل مصدر، مع أرقام الأسطر عند وجود ملف نصي.

1. استخراج القائمة الفعلية للأدوات من kilo debug agent.
2. إنشاء قائمة مرجعية للأسماء الحقيقية فقط.
3. مقارنة جميع قواعد permission بهذه القائمة.
4. تسجيل القواعد التي لا تقابل أداة فعلية — مثل list أو`lsp` أو`mcp` إذا ثبت غيابها في النسخة المثبتة — بوصفها قواعد محتملة الخمول.
5. عدم حذف هذه القواعد في مرحلة التدقيق.
1.4 مصفوفة الصلاحيات الفعلية
لا تكتفِ بجدول True/False. سجّل لكل وكيل، على الأقل، الأدوات التالية إذا كانت موجودة في النسخة الحالية:

لكل أداة سجّل:
- هل الأداة موجودة أصلًا؟
- هل هي متاحة للوكيل؟
- آخر قاعدة مطابقة وحاكمة، إن أمكن استخراجها.
- مصدر القاعدة: عام أو مشروع أو ملف وكيل أو افتراضي؛ مع توضيح مستوى الثقة.
- هل تتطلب موافقة (ask) أم تسمح (allow) أم تمنع (deny)؟
- هل توجد قيود أنماط أو مسارات؟
- هل يمكن تجاوز قيد أداة بواسطة أداة أخرى؟
فحص إلزامي لمسارات الكتابة: إذا كان bash مسموحًا، فلا تعتبر edit المقيد بامتدادات أو مسارات ضمانًا كاملًا لنطاق التعديل. يجب تسجيل أن Bash قد يتيح الكتابة عبر أوامر الصدفة، والتحقق من قواعد Bash الفعلية قبل وصف الوكيل بأنه محدود إلى مجلد أو امتداد معين.

فحص إلزامي للموافقة: إذا نص Prompt على أن كل تعديل يحتاج موافقة، فتحقق من أن edit و`write` والأدوات الأخرى تفرض هذه الموافقة تقنيًا. bash: ask لا يثبت أن edit نفسه يحتاج موافقة.
1.5 تدقيق محتوى Prompts
لكل وكيل وظيفي وإضافي:
1. استخراج نص Prompt الفعّال كاملًا أو الأجزاء الجوهرية منه داخليًا عند الحاجة، مع عدم عرض أو حفظ أي قيمة حساسة قد تكون مدرجة فيه؛ تُعرض مقتطفات منقحة فقط.
2. قياس هل يوجد Prompt فعلي، وعدم الاعتماد على الوصف description بديلًا عنه.
3. تحديد هل توجد تعليمات عربية صريحة.
4. تحديد هل يتعارض نص التعليمات مع أداة ممنوعة أو صلاحية أوسع مما يتطلبه الدور.
5. استخراج القيود والممنوعات ومسار الإبلاغ عن التعذر.
6. عدم افتراض أن AGENTS.md أو تعليمات الجلسة تُورّث إلى الوكلاء الفرعيين ما لم يوجد دليل فعلي.
7. تحديد أي Prompt يطلب من الوكيل تجاهل تعليمات أخرى، وفحص نطاق هذا الاستثناء بدقة.
1.6 تدقيق الأدوار والتداخلات
يُفحص الفصل بين الأدوار التالية تحديدًا:
- forensic-audit مقابل code-reviewer.
- debug مقابل incident-remediation.
- code مقابل frontend-specialist.
- architect مقابل orchestrator.
- explore مقابل forensic-audit.
- general مقابل المتخصصين الأحد عشر.
لكل تداخل، سجّل: نوع المهمة، من يستقبلها، من يجمع الأدلة، من يقرر، من ينفذ، ومن يراجع. لا تعتبر التشابه في أدوات القراءة وحده تداخلًا وظيفيًا.
1.7 تقييم التشغيل الفعلي المتاح من الأدلة
افصل بين ثلاثة مستويات:
1. Static: الإعدادات والتعريفات والصلاحيات الفعلية.
2. Tool-use: هل استدعى الوكيل أداة حقيقية وأعاد دليلًا صحيحًا؟
3. Role-performance: هل أنجز مهمة ممثلة لدوره بمخرج صحيح، دون تجاوز الحدود؟
سجّل النتائج السابقة المعروفة:
- Code نفّذ قراءة فعلية وجمع بيانات CLI.
- Ask قرأ ملفًا كاملًا باستخدام read بعد منع Bash.
- Explore شغّل مستقلًا واستخدم read و`glob` وصحح مسارًا غير صحيح.
- Forensic Audit قرأ ملفًا فعليًا باستخدام read.
- Architect توقف مرتين أثناء فحص واسع؛ لا يُستنتج من ذلك وحده أن صلاحيات القراءة معطلة.
- بقية الوكلاء: لا تصنفهم ناجحين أو فاشلين إلا وفق أدلة مباشرة.
المخرجات الإلزامية
تُعد المخرجات في التقرير أولًا؛ ولا تُنشأ ملفاتها داخل المستودع إلا بعد إذن المالك الصريح بإنشاء ملفات المرحلة الأولى المحددة. لا يُفهم الإذن بحفظ `MASTER_PLAN.md` على أنه إذن بإنشاء أي من هذه الملفات.
- AGENT_INVENTORY.md: القائمة الكاملة ومصدر كل تعريف.
- EFFECTIVE_PERMISSIONS_MATRIX.md: مصفوفة الصلاحيات الفعلية والقواعد الحاكمة والقيود.
- PROMPT_AUDIT.md: نصوص الأدوار والتوجيه العربي والتعارضات.
- ROLE_OVERLAP_ANALYSIS.md: حدود المسؤوليات والتداخلات.
- EVIDENCE_REGISTER.md: رقم دليل لكل نتيجة، ومصدره، وتاريخه، ودرجة الثقة.
- OPEN_ISSUES.md: المسائل غير المحسومة وأسباب عدم حسمها.
معيار القبول وبوابة المرحلة الأولى
- كل عنصر في kilo agent list مدرج.
- لا يوجد ادعاء عن مصدر تعريف أو صلاحية دون دليل.
- كل أداة غير موجودة أو قاعدة خاملة محتملة موثقة دون حذفها.
- حالات Bash/Edit/Write/Task والموافقة ومسارات الملفات مفهومة لكل وكيل أساسي.
- تم الفصل بين المؤكد والاستنتاج وغير المحسوم.
- لا تعديلات على إعدادات الوكلاء خلال التدقيق.
قرار المالك المطلوب: اعتماد تقرير التدقيق وقائمة المشكلات قبل تصميم الحالة المستهدفة.
المرحلة الثانية: إعادة اعتماد التصميم وبطاقات الأدوار
الهدف
تحويل نتائج التدقيق إلى تصميم مستهدف واضح يوافق عليه المالك قبل أي تعديل. هذه المرحلة قرارات تصميم، وليست تنفيذًا.
وضع Kilo الموصى به
Architect لإعداد التصميم بعد تزويده بتقارير المرحلة الأولى جاهزة؛ لا يُكلّف بإعادة جمع CLI أو فحص كل الملفات من الصفر. يراجع المالك النتائج ويعتمد البطاقات. إذا توقف Architect، يُسجل التعذر ولا تُكرر المهمة نفسها بلا تغيير؛ يمكن إعداد مسودة التصميم يدويًا من الأدلة المعتمدة، ثم عرضها على المالك.
2.1 بطاقة موحدة لكل وكيل
يجب أن تحتوي بطاقة كل وكيل على الحقول الآتية:
1. الاسم والمعرّف الفعلي.
2. الفئة: متخصص، منسق، عام، أو تقني مدمج.
3. المهمة الأساسية بجملة واحدة.
4. أنواع الطلبات التي يستقبلها.
5. ما يجب أن ينتجه.
6. ما يسمح له فعله.
7. ما يُمنع عليه فعله صراحة.
8. أدوات القراءة/البحث المطلوبة.
9. أدوات التنفيذ أو التعديل المطلوبة، إن وجدت.
10. حدود Bash وEdit وWrite وTask والموافقات.
11. قيود المسارات والامتدادات، إن وجدت.
12. mode المستهدف وسبب اختياره.
13. تعليمات اللغة العربية.
14. الملفات التي يُسمح له بقراءتها أو تعديلها بحسب الدور.
15. مسار التصعيد عند عدم القدرة أو اكتشاف مهمة خارج اختصاصه.
16. اختبار القبول الذي يثبت قيامه بدوره.
2.2 الحدود الوظيفية المستهدفة
تُعتمد الحدود التالية مبدئيًا ثم تُثبت أو تعدّل بموافقة المالك:
- Ask: يجيب ويشرح ويقرأ عند الحاجة؛ لا ينفّذ أوامر ولا يعدّل ملفات ولا يفوّض.
- Architect: يصمم ويخطط ويحدد البدائل والمخاطر؛ لا يغيّر كود التطبيق. يمكن السماح له بإنشاء وثائق خطط محددة فقط إذا اعتُمد ذلك صراحة.
- Forensic Audit: يجمع الوقائع ويحدد التسلسل والسبب الجذري بالأدلة؛ قراءة فقط، لا إصلاح ولا Bash ولا Task.
- Debug: يشخّص ويعيد إنتاج المشكلة ويحدد السبب ويقترح الإصلاح؛ الافتراضي ألا يغيّر الملفات وألا يفوّض. إن كان ثمة استخدام معتمد لإصلاح مباشر، يجب فصله في بطاقة مستقلة وموافقة صريحة.
- Incident Remediation: ينفذ إصلاحًا ضيقًا لحادثة مؤكدة فقط، بعد موافقة المالك على نطاق الملفات والتغيير؛ لا يتوسع ولا يعيد تصميم النظام.
- Code: ينفذ التغييرات البرمجية المعتمدة في النطاق المحدد؛ لا يقرر توسيع النطاق أو تفويض أعمال غير مطلوبة.
- Code Reviewer: يفحص التغييرات ويقدم ملاحظات مدعومة بمسارات وأسطر وأدلة؛ لا يصلح ولا يعدل ولا يشغّل اختبارات.
- Frontend Specialist: يعمل داخل الواجهة الأمامية فقط؛ يجب ألا تسمح صلاحية Bash الواسعة بتجاوز حدود ملفات الواجهة.
- Data: يبدأ بـNotebook-first، ويفصل التحليل عن تغيير التطبيق أو قاعدة البيانات؛ تُحدد مسارات المخرجات والعمليات المسموحة.
- Test Engineer: ينشئ ويعدّل الاختبارات ضمن نطاقها ويشغّلها؛ لا يغيّر كود الإنتاج إلا بتكليف مستقل. يجب ألا يُبطل Bash قيود ملفات الاختبار.
- Explore: يبحث ويستكشف ويقرأ ويجمع سياقًا؛ لا ينفذ كتابة أو نقلًا أو حذفًا. ويُحسم هل يكون subagent فقط أم all.
- Orchestrator: يحلل الطلب ويوزعه ويجمع النتائج ويعرض التعارضات؛ يسمح له بالتفويض عبر task، وتُمنع أدوات تعديل الملفات والتنفيذ المباشر.
- General: لا يُعتمد قبل قرار صريح: إما تعريفه كوكيل احتياطي محدود مع Prompt وصلاحيات معلومة، أو تعطيل استخدامه/حصره. لا يترك prompt_len=0 مع صلاحيات عامة واسعة.
2.3 سياسة الصلاحيات المستهدفة — مبادئ لا تغييرات تلقائية
هذه قواعد تصميم مقترحة؛ لا تُطبّق إلا بعد مراجعة المصفوفة الفعلية والحصول على الموافقة:
فئة الدور	القراءة/البحث	edit/write	bash	task
Ask / Forensic Audit / Code Reviewer / Explore	سماح بالقدر اللازم	منع	منع	منع
Architect	سماح	وثائق خطط محددة فقط إذا اعتمدت	منع افتراضيًا	منع افتراضيًا، إلا إذا اعتمد تفويض بحثي محدود
Debug	سماح	منع افتراضيًا	ask فقط للأوامر التشخيصية غير المدمرة إذا اعتمدت	منع افتراضيًا
Incident Remediation	سماح	ask أو آلية موافقة فعلية بعد اعتمادها	ask	منع
Code	سماح	سماح ضمن المهمة	حسب التكليف المعتمد	منع افتراضيًا؛ التنسيق عبر Orchestrator

Orchestrator	سماح	منع	منع	سماح للتفويض فقط

ملاحظات تقنية ملزمة:
- لا يُعتمد edit محدود المسارات بوصفه قيدًا كافيًا إذا كان bash: allow يسمح بكتابة غير مقيدة.
- لا يُعتمد edit: allow مع عبارة «اطلب موافقة المالك» إذا كان المطلوب موافقة تقنية قبل كل تعديل؛ يجب فحص دعم ask فعليًا وتأثيره على أداة Edit في Kilo 7.4.21.
- لا تُغيّر قيمة task إلا بعد تقرير من يحتاج التفويض فعلًا. المبدأ الافتراضي أن Orchestrator هو صاحب التفويض، وليس كل وكيل متخصص.
- لا تُمنح webfetch أو websearch أو أدوات أخرى لمجرد التوفر؛ تحدد الحاجة حسب الدور.
2.4 حسم القرارات المفتوحة
لا تنتقل المرحلة إلى التنفيذ قبل تسجيل قرار صريح بشأن:
1. هل General سيظل موجودًا؟ وما دوره وصلاحياته؟
2. هل Explore سيكون subagent فقط أم all؟
3. هل Debug تشخيص فقط؟ التوصية: نعم، مع نقل الإصلاح إلى Incident Remediation أو Code وفق نوع المهمة.
4. هل يملك Architect حق كتابة ملفات خطط Markdown فقط؟ وما المسارات المقبولة؟
5. هل يسمح لأي وكيل متخصص غير Orchestrator باستخدام task؟ وما المبرر؟
6. كيف تفرض موافقة المالك على تعديل Incident Remediation؟
7. كيف تضبط Bash لدى Frontend وTest وData بحيث لا تتجاوز حدود ملفاتها؟
8. ما مصدر الحقيقة القابل للمشاركة مع الفريق؟
9. هل توجد قواعد صلاحيات قديمة غير فعالة يجب حذفها، وما الدليل؟
10. ما اللغة المطلوبة في Prompts الوكلاء المدمجين والملفات العامة والمحلية؟
المخرجات الإلزامية
- TARGET_ROLE_CARDS.md: بطاقات الأدوار النهائية.
- TARGET_PERMISSION_MATRIX.md: المصفوفة المستهدفة بما فيها سبب كل صلاحية.
- SOURCE_OF_TRUTH_DECISION.md: قرار مصدر التعريف الرسمي وكيفية التعامل مع كل طبقة.
- DECISION_LOG.md: قرارات المالك والأسئلة التي حُسمت أو أُجلت.
- IMPLEMENTATION_SCOPE.md: قائمة دقيقة بالملفات والحقول المسموح تعديلها في المرحلة الثالثة.
معيار القبول وبوابة المرحلة الثانية
- لكل وكيل بطاقة مكتملة.
- لا يوجد تداخل غير محلول بين Debug/Incident أو Forensic/Reviewer أو Orchestrator/specialists.
- General محسوم، و`Explore` محسوم، وصلاحية task محسومة.
- صارت لكل صلاحية علة واضحة واختبار تحقق.
- وافق المالك على المصفوفة والملفات المسموح تعديلها.
قرار المالك المطلوب: اعتماد التصميم النهائي ونطاق التنفيذ؛ لا تعديل قبل ذلك.
المرحلة الثالثة: الإصلاح والتنفيذ المنضبط
الهدف
تنفيذ التصميم المعتمد فقط، مع أقل عدد ممكن من التغييرات، ومنع تغيير مصادر أو صلاحيات لم تدخل نطاق الموافقة.
أوضاع Kilo المستخدمة
- Code: لتعديل إعدادات الوكلاء وملفات المشروع وفق نطاق معتمد.
- Frontend Specialist / Data / Test Engineer: عند وجود تغييرات تخص مجالها حصريًا.
- Code Reviewer: لمراجعة الفروقات بعد التنفيذ دون إصلاحها.
- Forensic Audit: للتحقق القرائي من أدلة عدم تجاوز النطاق عند الحاجة.
لا تستخدم Architect كمنفّذ، ولا تستخدم Forensic Audit لتشغيل أوامر Bash، ولا تجعل Orchestrator يعدّل الملفات.
3.1 ترتيب التنفيذ الإلزامي
1. تثبيت مصدر الحقيقة الذي اعتمده المالك.
2. معالجة التعريفات المكررة أو المتعارضة، تعريفًا واحدًا في كل مرة، بعد إثبات المصدر الفعّال.
3. استكمال Prompts المفقودة أو غير المحددة، بدءًا من General إذا تقرر الاحتفاظ به.
4. إضافة توجيه عربي صريح إلى Prompts الفعالة لجميع الوكلاء المطلوب منهم التواصل بالعربية.
5. إزالة أي تعليمات تطلب أدوات ممنوعة، أو تعد بقدرات غير متاحة.
6. ضبط حدود Bash و`Edit` و`Write` و`Task` حسب المصفوفة المعتمدة.
7. معالجة قيود المسارات بحيث لا يُسمح عبر Bash بتجاوز حصر Frontend أو Test أو غيرهما.
8. ضبط Orchestrator كمنسق: task للتفويض، ومنع أدوات التعديل والكتابة والتنفيذ المباشر حسب التصميم المعتمد.
9. تطبيق قرار Explore و`General` و`Debug` و`Incident Remediation` كما اعتمده المالك.
10. تحديث وثائق الحوكمة ذات الصلة فقط إذا كانت ضمن IMPLEMENTATION_SCOPE.md.
3.2 قواعد التحرير الآمن
قبل كل مجموعة تغييرات، يجب على Kilo:
- إعادة فحص `git status --short` للتمييز بين تغييرات المالك السابقة وتغييرات المهمة الحالية.
- تحديد قائمة الملفات المسموح تعديلها حرفيًا، وعدم توسيعها دون موافقة جديدة.
- عدم استبدال أو تنسيق ملف كامل إذا كان يحتوي تعديلات سابقة غير معتمدة.
- حفظ Diff قبل/بعد أو وسيلة مقارنة موثوقة لكل مجموعة.
- التوقف إذا ظهر تغير غير متوقع في Git أو تعذر تحديد مالك التغيير.

1. لا تعدّل أكثر من مجموعة مترابطة واحدة في كل طلب Kilo.
2. عند التعامل مع .kilo/kilo.jsonc، اقرأ النص الخام أولًا، وتحقق من موضع كل استبدال وعدده (count == 1) قبل الكتابة.
3. إذا تعثرت أداة Edit بسبب تطبيع النص العربي، يمكن استخدام Python لتحرير دقيق، بشرط:
   - قراءة الملف الأصلي قبل التعديل.
   - استبدال مقاطع محددة فقط، لا إعادة كتابة الملف من الصفر.
   - التحقق من عدد التطابقات قبل الاستبدال.
   - حفظ UTF-8 والمحافظة على BOM ونهايات الأسطر والترتيب الأصلي كما كان.
   - إيقاف العملية إذا لم يطابق النص المتوقع.
4. لا تحذف تعريفًا عالميًا أو محليًا قبل إثبات أن البديل فعّال وأن حذفه لا يغيّر وكيلًا آخر.
5. لا تعدّل ~/.config/kilo/kilo.jsonc أو ~/.config/kilo/agents/ ضمن التنفيذ العادي؛ أي حاجة لذلك تُرفع كقرار مستقل.
6. لا تزل استثناء .kilo/kilo.jsonc من Git ولا تستخدم git add -f تلقائيًا.

9. تعليمات التشغيل المرحلي إلى Kilo Code
هذه الخطة مرجع حاكم بعد اعتمادها، وليست برومبتًا واحدًا لتنفيذ كل العمل. يُرسل إلى Kilo برومبت قصير لهدف واحد في كل مرة، وفق المرحلة المعتمدة حاليًا فقط. يجب أن يذكر المستخدم وضع Kilo المطلوب صراحة، ولا يغيّره Kilo من تلقاء نفسه.
1. استخدم Code لجمع حالة CLI وGit؛ لا تكلف Forensic Audit بتشغيل Bash وهو ممنوع منه.
2. استخدم Architect للتصميم بعد تسليمه أدلة جاهزة، لا لجمع كل الأدلة من الصفر.
3. استخدم Code أو المتخصص المناسب لتنفيذ تغيير معتمد فقط.
4. استخدم Test Engineer لاختبارات القبول، وCode Reviewer لمراجعة الفروقات.
5. استخدم Orchestrator للتفويض في اختبار التكامل، لا لتعديل الملفات.
6. اكتب كل تقارير Kilo بالعربية، مع أسماء الأدوات والملفات كما هي.
7. في نهاية كل طلب: اعرض ما نُفذ، وما لم يُنفذ، والأدلة، والملفات المتأثرة، ثم توقف.
8. لا تنتقل إلى مرحلة لاحقة ولا تنفذ توصية غير معتمدة. يجب أن يتضمن كل انتقال موافقة صريحة جديدة من المالك على رقم المرحلة ونطاقها.
9. إذا اكتشف Kilo سرًا أو ملفًا ملتصقًا أو تغييرًا غير متوقع، يتوقف عن النسخ والتنفيذ ويبلغ المالك دون كشف القيمة الحساسة.
10. لا يُفترض أن وجود `MASTER_PLAN.md` أو اكتمال نسخه يعني اعتماد الخطة أو المرحلة صفر.
