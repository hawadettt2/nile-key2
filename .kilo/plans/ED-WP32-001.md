**Date:** 2026-07-20

**Decision Owner:** Project Chief Architect  
**Review Authority:** Engineering Decision Board  
**Related Work Package:** WP-32 — Knowledge Graph  
**References:** PLAN.md, ED-WP30-002

## 1. Context

PLAN.md Section 6.2 Capability #10 describes the Knowledge Graph capability as: "رسم معرفي - عملاء، موردين، منتجات، علاقات" (Knowledge Graph — customers, suppliers, products, relationships).

The term "products" (منتجات) appears in PLAN.md in two contexts:
1. Business description: "تصدير المنتجات المصرية (خضار، فاكهة، منتجات غذائية)" — describing the company's commercial activity
2. Capability #10: listing "products" as one of the entity types in the Knowledge Graph

However, repository evidence shows:
- No `Product` Pydantic schema exists in `backend/app/schemas/`
- No `products` database table exists in `backend/app/core/database.py`
- No Product API endpoint or service exists in `backend/app/routers/` or `backend/app/services/`
- No approved graph model defines how products should be represented
- No Engineering Decision currently resolves this ambiguity

This creates a governance blocker: WP-32 Specification cannot be finalized without determining whether "products" is in scope and how it should be represented.

---

## 2. Decision

**WP-32 SHALL NOT implement Products.**

Products are deferred to a future Work Package until an approved Product domain model exists.

The definition of the complete Knowledge Graph node set is left to the WP-32 Specification.

---

## 3. Scope Impact

### In Scope

The complete Knowledge Graph node set, relationship types, and integration boundaries are defined in the WP-32 Specification.

### Out of Scope

- Products representation of any kind
- New standalone "products" entity table
- Product-specific graph nodes or edges
- Any assumption that "products" in PLAN.md Capability #10 refers to a separate entity

## 7. Consequences

### Positive

- Prevents scope creep into undefined Product domain
- Avoids technical debt from premature Product representation
- Preserves architectural integrity

- Follows established precedent (ED-WP30-002)

### Negative
- Capability #10 "products" keyword is not addressed in WP-32

- Future WP will need to define Product domain model before implementation

### Future Implications
- A future Work Package must define the Product domain model (schema, API, relationships) before products can be added to the Knowledge Graph
- When Product domain model is approved, a new Engineering Decision or Specification update will be required to add products to WP-32 or a subsequent WP

**Yes.** The ambiguity about "products" representation is resolved by explicit deferral. WP-32 Specification can now proceed without making assumptions about products.
