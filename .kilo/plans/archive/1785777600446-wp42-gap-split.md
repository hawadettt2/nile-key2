**Acceptance Criteria:**

## WP-42-C: Role-Based Workspace & Navigation Adaptation

**Problem:** All authenticated users land on the same Dashboard regardless of role. The sidebar shows all menu items to all users. External roles (`supplier`, `customer`) see internal modules like Digital Export Manager, Knowledge Graph, and Trade Intelligence.

**Scope:**
- Implement role-based default routing after login (role-specific workspace landing pages)
- Filter sidebar navigation items based on user role and permissions
- Hide or disable menu items the user cannot access
- Graceful handling of 403 errors from backend (redirect or permission message)
- Ensure navigation state management respects role changes

**Out of Scope:**
- Complete custom UI for every role
- Permission-based UI element hiding within individual pages (covered by existing RBAC)
- DEM authorization logic (covered in WP-42-A)

**Depends On:**
- WP-42-A (DEM role restrictions must be defined first)
- None — role routing rules approved; ready for execution

**Priority:** MEDIUM

**Approved Routing Rules:**

| Role | Default Page After Login | Notes |
|------|--------------------------|-------|
| `owner` | `/digital-export-manager` | Internal role; full access including DEM |
| `manager` | `/digital-export-manager` | Internal role; full access including DEM |
| `sales` | `/customers` | Internal role; DEM allowed |
| `admin_staff` | `/documents` | Internal role; DEM allowed |
| `accountant` | `/invoices` | Internal role; DEM allowed |
| `logistics` | `/shipments` | Internal role; DEM allowed |
| `supplier` | `/profile` | External role; DEM/KG/TI hidden |
| `customer` | `/profile` | External role; DEM/KG/TI hidden |
| Any other/undefined role | `/` | Dashboard fallback |

**403 Handling:**
- Route-level: Redirect to `/` with clear permission toast/message
- Action-level: Permission message inside the page; no redirect

**Layout Strategy:**
- Single shared Layout for all roles
- `visibleNavItems` computed dynamically from `user.role`

**Acceptance Criteria:**
- [ ] Each role lands on its approved default page after login

- [ ] `supplier` lands on `/profile`
- [ ] `customer` lands on `/profile`
- [ ] Any undefined role falls back to `/` (Dashboard)
- [ ] `supplier` and `customer` cannot access DEM, Knowledge Graph, or Trade Intelligence via navigation
- [ ] Internal roles can access DEM, Knowledge Graph, and Trade Intelligence
- [ ] Route-level unauthorized access redirects to `/` with a clear permission message

## Critical Clarifications Before Execution

### Items That Are Implementation Fixes, Not Product Decisions

The following gaps are **security bugs or code defects**, not product decisions requiring Project Owner approval:

| Gap | Issue | Required Action |
|-----|-------|-----------------|
| `/tools` unauthenticated | `GET /api/v1/digital-export-manager/tools` has no auth dependency (`digital_export_manager.py` lines 314-320) | **Must fix** — add `get_current_user` |
| DEM core open to supplier/customer | DEM core endpoints (`/connect`, `/missions`, `/sessions`, `/sessions/{id}`) accept any authenticated user (`digital_export_manager.py` lines 92-110, 112-221, 223-244, 281-311) | **Must fix** — restrict to internal roles only |
| Default role mismatch | `database.py` line 450 defaults to `staff`, but seeded roles do not include `staff`; `schemas/user.py` line 16 defaults to `Customer` | **Must fix** — align to a single default |

### Registration Policy: Decision Adopted — Approval Workflow

The `/register` endpoint (`auth.py` lines 75-95) accepts an arbitrary role string without validation. Product Owner decision: **adopt Approval Workflow**.

**Policy:** Public registration creates an account with `is_active=0` (pending). The account does not become active until reviewed and approved by authorized personnel per the existing RBAC system. Role assignment is determined during approval, not supplied by the client.

**Existing RBAC Reference (governs review, approval, and role assignment):**
- `auth.py` lines 67-72: `require_role` decorator — the existing authorization mechanism.
- `digital_export_manager.py` lines 350-389: `/approvals` endpoints demonstrate the existing approver pattern (`owner`, `manager`).
- `roles.py` lines 12-101: `/roles` endpoints demonstrate existing role-management authority (`owner` for write, `owner`+`manager` for read).
- `database.py` line 450: `is_active` field on `users` table already supports activation/inactivation.

Track B implementation must reuse these existing files and conventions. No new roles, permissions, endpoints, or RBAC rules may be introduced.

Track B of WP-42-A is now unblocked. Track A (security fixes) remains unblocked and can proceed in parallel.

### DEM Authorization: Evidence-Based Recommendation

**Recommended model: DEM is restricted to internal roles only.**

Evidence from codebase:
- `main.py` line 119: API title is "Digital Export Manager API — Intelligent Operating Platform for export operations"
- DEM health endpoint (`digital_export_manager.py` lines 73-89) lists internal AI components: `reasoning_engine`, `task_planner`, `execution_engine`, `company_knowledge`, `long_term_memory`
- Seeded roles (`database.py` lines 850-859) clearly separate internal (owner, manager, sales, admin_staff, accountant, logistics) from external (supplier, customer)
- External role permissions are minimal: `supplier` → `profile:read,profile:write`; `customer` → `profile:read,invoices:read,shipments:read`
- DEM exposes company knowledge, AI reasoning, memory, and execution capabilities — these are internal company assets

**Conclusion:** DEM should be restricted to internal roles: `owner`, `manager`, `sales`, `admin_staff`, `accountant`, `logistics`. External roles (`supplier`, `customer`) should access only their scoped ERP pages (Invoices, Shipments, Profile) through the existing authenticated routes.

This is an **evidence-based architectural constraint**, not merely a product preference.

## Updated WP Descriptions

### WP-42-A: DEM Authorization Hardening (UPDATED)

**Problem:** DEM core functionality is accessible to any authenticated user. The `/tools` endpoint has no authentication. The register endpoint allows arbitrary role assignment without validation.

**Scope:**

**Track A — Security Fixes (immediate, no Product Owner decision required):**
- Add `require_role(["owner", "manager", "sales", "admin_staff", "accountant", "logistics"])` to DEM core endpoints (`/connect`, `/missions`, `/sessions`, `/sessions/{id}`)
- Add `get_current_user` to `/tools` endpoint
- Update frontend to hide/disable DEM features for unauthorized roles
- Ensure `supplier` and `customer` roles cannot access DEM

**Track B — Registration Policy (unblocked; Approval Workflow adopted):**
- `/register` endpoint must create accounts in `is_active=0` (pending) state
- The request must not include an arbitrary role assignment from the client; role assignment is determined during approval
- Approved accounts become active and receive their assigned role
- Implementation must follow existing RBAC conventions for who may review, approve, and assign roles
- No new roles, permissions, or approval endpoints may be introduced outside the existing RBAC reference

**Out of Scope:**
- Modifying existing ERP role permissions
- Adding new roles to the system
- Changing default user role (`staff`)
- DEM internal architecture changes
- Public website (WP-42-B)

**Depends On:**
- Track A: None — these are security fixes based on existing architecture
- Track B: None — policy decision adopted; implementation unblocked

**Priority:** CRITICAL

**Migration / Rollout Considerations:**
- **Existing DEM sessions:** When authorization is hardened, existing `agent_sessions` records created by `supplier`/`customer` roles remain in the database but become inaccessible to those users. Consider a data retention policy: either delete orphaned sessions or archive them for audit.
- **Backward compatibility:** Frontend must handle 403 responses gracefully. Users who previously had DEM access will see a permission message instead of the DEM interface.
- **Audit trail:** All 403 attempts should be logged via existing audit infrastructure for security monitoring.
- **Frontend hide vs backend reject:** Frontend should hide DEM navigation for unauthorized roles, but backend must still enforce authorization. Never rely on frontend hiding as a security control.

**Acceptance Criteria:**

**Track A — Security Fixes:**
- [ ] `POST /api/v1/digital-export-manager/connect` returns 403 for `supplier`/`customer` roles
- [ ] `POST /api/v1/digital-export-manager/missions` returns 403 for unauthorized roles
- [ ] `GET /api/v1/digital-export-manager/tools` requires authentication
- [ ] Frontend hides DEM navigation items for unauthorized roles
- [ ] Unauthorized API attempts are logged via audit

**Track B — Registration Policy (Approval Workflow):**
- [ ] `POST /api/v1/auth/register` creates inactive account (`is_active=0`) instead of active user
- [ ] Registration request stores role assignment request for review (no arbitrary client-side role)
- [ ] Authorized reviewers (per existing RBAC) can view pending registrations
- [ ] Authorized approvers (per existing RBAC) can activate accounts and assign roles
- [ ] Unapproved accounts cannot authenticate
